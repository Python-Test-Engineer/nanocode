Nanocode, explained

A chapter-by-chapter walkthrough of a small coding agent, written for students.

This is the companion book to the code in this repository. It assumes you have the code open beside it. Each chapter explains one new idea, shows the code that implements it, walks through what happens when the program runs, and ends with things to try and questions to check yourself against.

The repository is an educational refactor of Build Your Own Coding Agent: the chapters and their ideas are the book's, the structure is not. Every chapter's original single file is kept as nanocode_copy.py, so you can diff the refactor against the source at any point.

How to use this book

Three ways, all valid:

  1. Cover to cover. Read chapters 1-12 in order. Each builds on the last, and nothing is assumed except basic Python.
  2. Alongside the code. Open chNN/nanocode.py and the chapter here at the same time. Every section names the file and function it is talking about.
  3. As a reference. Appendix A is the whole architecture on one page; Appendix B is a glossary; the checkpoint boxes answer the questions students actually ask.

Conventions used here

  • Diagrams are plain ASCII. They render identically in Markdown, in book.html, in a terminal and on paper — no diagram plugin required.
  • ──► is data flow, ▼ is time moving down. Boxes are components; the text inside is what is passed between them.
  • Frame-by-frame traces are real program output, split into "frames". Read them top to bottom; they are the animation.
  • Hook lines (⟡ hook:tool_call ...) are printed by this fork, not by the original book. They are on by default; NANOCODE_HOOKS=0 hides them.
  • Collapsible answers use HTML <details>. In a plain terminal view you will see the tags — read around them.
  • Snippets are excerpts, not photocopies. Long expressions are sometimes joined onto one line, ... marks omitted code, and comments are occasionally added for the point being made. The files themselves are the source of truth.

Chapter 1 — The event loop (there is no AI yet)

You are here: nothing talks to a model. This chapter builds the shape every later chapter plugs into: read a line, hand it to an Agent, print what comes back, repeat until the user leaves.

That sounds trivial, and it is — which is exactly why it is chapter one. Every agent you have ever used is this loop with more interesting things happening inside step 2.

The idea in one picture

        ┌──────────────────────────────────────────────┐
        │                 main() loop                  │
        │                                              │
        ▼                                              │
  ui.ask()  ──►  Agent.handle_input(text)  ──►  ui.answer(output)

                     │ "/q" ?                            │

Agent is deliberately empty of intelligence. It records nothing, remembers nothing, and calls nothing:

class Agent:
    """A coding agent that processes user input."""

    def __init__(self):
        pass

    def handle_input(self, user_input):
        if user_input.strip() == "/q":
            raise AgentStop()

        if not user_input.strip():
            return ""

        # Chapter 1 has no model behind the curtain. Returning the input proves
        # the plumbing works: something reads, something answers, something draws.
        return f"You said: {user_input}\n(Agent not yet connected)"

Why it is built this way

Quitting is an exception, not a flag. /q can be typed at a prompt deep inside a future chapter, and the only code that cares is main(), which catches AgentStop once. A boolean running = False would have to be threaded through every layer.

Empty input returns "", not a message. main() only prints when there is something to print, so pressing Enter does not produce a stray blank line.

All printing goes through ui.py. The book uses print() here. This version calls ui.answer(...) so that later chapters can restyle output without touching the loop — the loop should not know what a colour is.

Checkpoint

Why does handle_input return a string instead of printing? Because "produce the answer" and "draw the answer" are different jobs. Returning a string means the agent can be tested without a terminal, and `main()` decides how the answer appears. Every later chapter keeps this split: `Agent` returns, `ui` renders.
What would break if Agent printed directly? The tests. `test_nanocode.py` calls `handle_input` and asserts on the *return value*; printed text would be invisible to them. It would also duplicate output the moment a chapter wants to render Markdown instead of plain text.

Chapter 2 — First contact (one raw request)

You are here: still no agent. This chapter sends a single HTTP request to a model and prints the JSON that comes back, so you can see exactly what a "brain" looks like before any abstraction hides it.

The book does this with Claude. This fork does it with OpenRouter, because the same key then drives every later chapter. The mechanics are identical — a URL, a key, a JSON body, a JSON reply.

The idea in one picture

      { model, messages }                                            │

No loop, no tools, no memory. If you understand this arrow diagram, every chapter after this one is bookkeeping.

Why it is built this way

No error handling on purpose (mostly). The book fires the request "with no safety net". Chapter 4 adds retries. Here, a 401 should be loud — you are meant to see what a failure looks like before you start hiding failures.

The JSON is printed, not summarised. An abstraction you have not seen the insides of is a superstition. Once you have read choices[0].message, chapter 3's Thought object reads like a translation, not a trick.

The key never appears in output. ui.error prints the provider's message on failure, not the request — a small habit worth copying.

Checkpoint

Why is max_tokens in the request if the model already knows when to stop? Because it caps cost and latency. A model will happily write 2000 tokens when 20 would do; `max_tokens` is your budget, and hitting it shows up as `finish_reason: "length"` — a truncated reply, not an error.
What does the model actually receive from you? The messages array, serialised as JSON, plus the model name. No files, no memory, no state: everything the model knows about your project is whatever you literally put in those messages. That fact is the whole reason tools exist.

Chapter 3 — The first brain (and the conversation becomes memory)

You are here: the request from chapter 2 becomes a class, and the class's output becomes a Thought. The agent now remembers what you said — because it resends the whole conversation every turn.

This is the first chapter where behaviour feels like magic. It is not. The model has no memory; the list has the memory, and you send it again and again.

The idea in one picture

  turn 1                     turn 2                     turn 3
  ──────                     ──────                     ──────
  conversation = []          conversation = [           conversation = [
    + user "my name is Sam"      user  "my name is Sam"      user  "my name is Sam"
                                 assistant "Hello Sam"      assistant "Hello Sam"
                                 + user "what is my name?"  assistant "Your name is Sam"
                                                            + user "and again?"
                                                          ]
        │                          │                          │
        ▼                          ▼                          ▼
   brain.think(conv)  ─────►  brain.think(conv)  ─────►  brain.think(conv)

The arrow into brain.think always carries everything. That is the memory.

The brain, and the object it returns

class OpenRouter:
    def think(self, conversation):
        headers = {...}
        payload = {"model": self.model, "max_tokens": 4096, "messages": conversation}
        response = requests.post(self.url, headers=headers, json=payload, timeout=120)
        response.raise_for_status()
        return self._parse_response(response.json()["choices"][0]["message"])

The important line is the last one: the raw provider JSON never leaves this class. The agent receives a Thought:

class Thought:
    def __init__(self, text=None, tool_calls=None, thinking=None):
        self.text = text              # what to show the user
        self.tool_calls = tool_calls or []  # empty here; tools arrive in ch05
        self.thinking = thinking      # reasoning, for the dim 💭 lines only

That empty tool_calls list is a promise being made early: the loop already knows it might be asked to run something.

The agent, and the list that remembers

self.conversation.append({"role": "user", "content": user_input})

try:
    thought = self.brain.think(self.conversation)
    ui.thinking(thought.thinking)

    text = thought.text or ""
    self.conversation.append({"role": "assistant", "content": text})
    return text
except Exception as e:
    self.conversation.pop()   # the question never got an answer: drop it

Two details students usually miss:

  1. The reply is appended too. If you only append user messages, the next request contains a conversation where the model talks to itself.
  2. A failed call pops the user message. Otherwise the history has two user turns in a row, and some providers reject that outright.

The brain moved to llm.py even though there is only one provider. Chapter 4 adds two more; moving a class while it is still small is cheap, moving it later is a refactor.

Thought has exactly three fields. Every one of them is used by the agent or the UI this chapter. Fields are added when a chapter needs them (raw_content in ch05, token counts in ch09) — not in advance.

Hooks exist from the first brain onwards. They are the cheapest way to make the loop legible: five emit calls in the agent, and any listener can watch.

Checkpoint

Where does the model's "memory" actually live? In `Agent.conversation` — a plain Python list on your machine. The model is stateless between requests; resending the list is what feels like memory. This is also why long conversations get expensive: every turn resends everything.
Why does a failed call remove the user message? A conversation with a dangling user question has the wrong shape: two user messages in a row on the next attempt. Removing it keeps the alternation user/assistant/user that providers expect.
What is thinking for, if it is not sent back? It is shown once, dimmed, then dropped. Reasoning is produced by the model, but you do not need to replay it — the answer (and later the tool calls) carry the information forward. Keeping it would inflate every subsequent request.

You are here: the agent stops knowing which model answers it. A Brain is now a contract, providers are implementations, and /switch swaps them mid-conversation.

Claude and DeepSeek differ only in URL, headers and payload — the parsing is identical, so it lives in the base class. OpenRouter speaks a different dialect and overrides _parse_response. The base class is doing exactly one job: naming the shared parts.

Retries: three cases, three behaviours

requests raises RequestException        -> network died: wait 2**attempt, retry
status 429 or >= 500                    -> server busy: wait Retry-After (or 2**attempt), retry
status >= 400                           -> our request is wrong: raise, do not retry

The distinction matters: a 429 is "later", a 401 is "never". Retrying the second one just wastes ten seconds before failing anyway.

/switch — and why the history survives

names = list(BRAINS.keys())              # cycle order = dict order
idx = names.index(self.brain_name)
new_name = names[(idx + 1) % len(names)]

self.brain = BRAINS[new_name]()          # construct inside try: no key -> ValueError
self.brain_name = new_name

At this chapter the conversation is plain {"role", "content"} text, so every provider can read it and nothing has to be translated. Chapter 5 changes that: tool calls force the two dialects apart, and llm.py grows translation functions.

Why it is built this way

The registry is an ordered dict, not a list of tuples. /switch needs an order and main() needs a lookup; one structure serves both.

Construction happens inside the try. A missing key raises ValueError at __init__ time, so the switch must be able to fail without corrupting the agent.

The base class holds no state. Its context_limit/last_input_tokens are placeholders for chapter 9; a provider is otherwise a pure request builder.

Checkpoint

Why not put the retry loop inside each provider? Because it is the same retry loop. Duplicating it three times means three places to fix when a provider adds a new status code. A tool is metadata plus a function

class ReadFile:
    name = "read_file"
    description = "Reads a file from the filesystem. Use this to examine code."
    input_schema = {
        "type": "object",
        "properties": {"path": {"type": "string", "description": "The path to the file"}},
        "required": ["path"],
    }

    def execute(self, path):
        ui.tool_action("read_file", path)
        try:
            with open(path, "r", encoding="utf-8") as f:
                lines = f.readlines()
            numbered_lines = [f"{i+1} | {line}" for i, line in enumerate(lines)]
            return "".join(numbered_lines)
        except Exception as e:
            # A tool must always return a string. The model reads the error
            # and decides what to do next.
            return f"Error reading file: {e}"

Four things to notice:

  • description and input_schema are prompt engineering, not documentation. They are pasted into the request; the model chooses tools by reading them.
  • execute never raises. A traceback ends the turn; "Error: File not found" continues it.
  • The line numbers (1 | import os) are for the model, so it can refer to "line 42" later.
  • ui.tool_action(...) is the only console call in tools.py. Colour lives in ui.json, so a tool never mentions a colour.

The class

class Memory:
    """Persistent scratchpad for the agent."""

    def __init__(self, path=".nanocode/memory.md"):
        self.path = path
        self._ensure_exists()
        self.content = self._load()

    def save(self, content):
        self.content = content                      # in memory
        with open(self.path, "w", encoding="utf-8") as f:
            f.write(content)                        # on disk

content is kept in sync with the file so the next request does not have to re-read it. That is the whole class — about twenty lines.

    The whole safety harness is this list comprehension: in plan mode the model

  • once (count=1) — repeated snippets do not all change at once
  • refuses loudly — the model gets a message it can act on ("text not found"), then usually reads the file again and retries with the right quote

run_command: stdout, stderr, timeout, and no exceptions

result = subprocess.run(
    command,
    shell=True,            # the model writes shell syntax: "python x.py && pytest"
    capture_output=True,   # keep output OUT of the console, IN the tool result
    text=True,
    timeout=int(os.environ.get("NANOCODE_TIMEOUT", "30")),   # a hung command must not hang the agent
    cwd=os.getcwd(),
)

output = ""
if result.stdout: output += f"STDOUT:\n{result.stdout}\n"
if result.stderr: output += f"STDERR:\n{result.stderr}\n"
if not output:    output = "(No output)"

capture_output=True is the key: the agent needs the text, and your terminal does not. A non-zero exit code is not an error here — it is evidence. The model reads STDERR, edits the file, and runs again.

Compaction: budgeting the context window

# in the loop, after each reply
if self.brain.last_input_tokens > self.brain.context_limit * 0.75:
    self._compact_conversation()

# in _compact_conversation
history = "\n".join(f"{m['role']}: {str(m['content'])[:500]}" for m in self.conversation)
prompt = [{"role": "user", "content": f"Summarize this conversation for continuity...\n\n{history}"}]
saved_tools, self.brain.tools = self.brain.tools, []     # no tools for bookkeeping
try:
    thought = self.brain.think(prompt)
finally:
    self.brain.tools = saved_tools
self.conversation = [{"role": "user", "content": f"Previous conversation summary: {thought.text}"}]

Read the last line carefully: history is replaced by a summary. You lose detail, you keep continuity, and you gain room to work. That is the trade.

last_input_tokens is real data from the response (usage), not an estimate. Estimating tokens with a character count is the classic way to be surprised by a 400 at the worst moment.

Why it is built this way

The exit code is not an exception. Throwing on a non-zero exit would delete the most useful information in the loop. The agent is supposed to see failures.

Compaction summarises instead of truncating. Dropping old messages loses the decisions; summarising keeps them at a fraction of the tokens.

The threshold is 75%, not 100%. By the time you are at 100% the request has already failed. Headroom is where the summariser fits.

Checkpoint

Why is a failed test "information" rather than an error? Because the loop exists to react to output. If failures raised exceptions, the turn would end at the most interesting moment. Strings let the model decide: retry, change approach, or report back to you.
What exactly survives a compaction? Only the summary message. It is asked to preserve what was accomplished, what is in progress, and key decisions — so file paths and intent usually survive, exact code does not. If a task depends on verbatim content, re-read the file after compaction.
Why remove the tool menu while summarising? The summary request is bookkeeping, not a task. Leaving tools on invites the model to call one mid-summary, which would then be appended to the very history you are about to throw away.

The class, and the one interesting line

class Ollama(Brain):
    """Ollama local model (Anthropic-compatible API, with tool support)."""

    context_limit = 32_000

    def __init__(self, memory=None, tools=None):
        super().__init__(memory, tools)
        self.model = os.getenv("OLLAMA_MODEL", "qwen3-coder:30b")
        self.url = "http://localhost:11434/v1/messages"   # no auth, no TLS
        self._detect_context_limit()

def _detect_context_limit(self):
    """Query Ollama for the model's context window size."""
    try:
        response = requests.post("http://localhost:11434/api/show",
                                 json={"model": self.model}, timeout=0.5)
        for key, value in response.json().get("model_info", {}).items():
            if key.endswith(".context_length"):
                self.context_limit = value
                return
    except Exception:
        pass  # the daemon may not be running; keep the default

Why this exists at all: chapter 9's compaction compares last_input_tokens > context_limit * 0.75. With a hosted model you know the window; with a local model the window depends on the model file you loaded. So we ask the daemon, and fall back to a conservative 32k.

The timeout=0.5 is not sloppiness — it is a probe. If Ollama is not running, the probe should cost half a second, not block the chapter.

The tool

class SearchWeb:
    name = "search_web"
    plan_safe = True     # read-only: research belongs in plan mode too
    description = ("Searches the internet for current information. Use when you "
                   "need knowledge beyond your training data.")
    input_schema = {"type": "object",
                    "properties": {"query": {"type": "string"}},
                    "required": ["query"]}

    def execute(self, context, query):
        ui.tool_action("search_web", f"'{query}'")
        backend = resolve_ddgs()
        if backend is None:
            return "Error: ddgs package not installed. Run: pip install ddgs"
        results = backend().text(query, max_results=3)
        formatted = [f"Title: {r['title']}\nURL: {r['href']}\nSummary: {r['body']}\n"
                     for r in results]
        return "\n".join(formatted)

Three deliberate choices:

  • max_results=3. The output is going into a prompt; ten results is a lot of context for a small gain.
  • Title / URL / Summary on separate lines. Easy for the model to cite, easy for you to read in a trace.
  • plan_safe = True. Reading the web changes nothing locally, and research is exactly what plan mode is for.

The test hook (resolve_ddgs)

def resolve_ddgs():
    """The DuckDuckGo backend, honouring an override on the host module."""
    global DDGS
    host = sys.modules.get("nanocode")
    if host is not None and getattr(host, "DDGS", None) is not None:
        DDGS = host.DDGS
    return DDGS

The book's tests patch nanocode.DDGS while the tool lives in tools.py. Looking the name up at call time (instead of binding it at import) keeps both honest and costs nothing outside tests. It is also a small lesson in why monkeypatching and module-level globals are such close friends.

Appendix B — Glossary

Brain — a provider behind one method, think(conversation) -> Thought. The agent never knows which one it is talking to.

content blocks — the Anthropic message shape: a list of {"type": "text"}, {"type": "tool_use"}, {"type": "tool_result"} dicts. This fork stores history in this shape for every provider and translates at the edge.

compaction — replacing long history with a summary when the context window fills (chapter 9). Keeps continuity, loses detail.

dialect — a provider's wire format. Anthropic and DeepSeek accept content blocks; OpenRouter uses OpenAI chat-completions. to_openai_messages() converts.

hook — a passive observer of the loop: turn_start, before_think, after_think, tool_call, turn_end. Return values are ignored; a hook that raises is reported and skipped.

plan mode — the mode where only plan_safe tools are offered to the model. The enforcement is the tool menu, not the prompt.

raw_content — the provider's own response blocks, stored verbatim in history so tool results keep referring to real tool-call ids.

Thought — the only object a brain returns: text, tool calls, raw content, reasoning.

ToolContext — the small object passed to every tool; today it carries Memory, tomorrow whatever else a tool is allowed to see.

tool_result — the block that carries a tool's string output back to the model, paired with the tool_use_id of the call that requested it.
